# Plan: Revive Public Jobs Scraper DB Locally with Supabase (2026-05-22)

**Goal**: Get a fully working local PostgreSQL + PostgREST database (matching the exact interface expected by all 14 upload scripts) so the user can immediately test one jurisdiction end-to-end and then perform a fresh data pull. No code changes to scrapers or uploaders.

**Decision**: Use `supabase start` (local dev stack) inside this repo. The old cloud project (pkffbxwbnayfuqskhdaw) is deactivated and unresumable. A new cloud project is unnecessary; local gives zero-cost, offline, reproducible hosting "in this dir" with 100% compatibility.

**Why not restore the backup?** "DB Cluster Backup Aug 26 2025.gz" contains old, incompatible table schemas (long names like `british_columbia_jobs`, fewer columns, no JSONB arrays / triggers / RLS). Restoring it would conflict with Supabase-managed schemas (`auth`, `storage`, etc.) and break current upload logic. We treat it as a read-only archive only.

## 6. (Optional) Legacy Backup Archive + "Can we restore the backup data via upsert?"

**Direct answer to your question**:  
No, we cannot simply restore the `DB Cluster Backup Aug 26 2025.gz` and run the existing `upload_to_supabase.py` upserts against it.

Reasons (from inspection of the dump + current schemas):
- The backup contains **old table definitions** (`british_columbia_jobs`, `manitoba_jobs`, `tasmania_jobs`, etc.) with 2025-era columns (mostly flat text/varchar, no JSONB arrays, different field names).
- Current code expects the **new short-named tables** (`bc_jobs`, `man_jobs`, `tas_jobs`, …) with the rich modern schema (BIGSERIAL + many JSONB columns, triggers, indexes, RLS on some tables).
- Even the tables that share names (`vic_jobs`, `nsw_jobs`, `goc_jobs`, `uk_jobs`) have drifted — the backup rows would fail to insert into the current `CREATE TABLE` statements.
- The Python uploaders do **not** read from the DB backup at all; they read the `data/*/jobs_json/*.json` files produced by the scrapers and do their own transform + `.upsert()`.

**Recommended "upsert historical data" path (already the intended one)**:
- The repo already has the real backup of your scraped work: `data/` (656 MB, 8 463 files, including `VIC/jobs_json/`, `NSW/jobs_json/`, `UK/jobs_json/`, etc.).
- Running the current `upload_to_supabase.py` scripts on those JSON files **is** the upsert of historical data, now mapped into the correct modern schema by the transform logic that lives in each uploader.
- This is exactly what you will do on your next data pull anyway.

**If you still want the exact 2025 rows in their original shape** (for archive / diff / research):
1. Spin up a throw-away plain Postgres (docker or `createdb archive_2025`).
2. `gunzip -c "DB Cluster Backup Aug 26 2025.gz" | psql -d archive_2025` (or restore only the public old *_jobs tables).
3. Write a small one-off Python script (using psycopg2 or pandas + the supabase client) that:
   - Reads each old table,
   - Maps the columns to the equivalent new schema (best-effort; some fields will be NULL or concatenated into JSONB),
   - Calls the same upsert pattern.
4. Point that script at your local Supabase (`SUPABASE_URL=http://127.0.0.1:54321` + service key) and run it once.

This migration script is **not** part of the current plan unless you explicitly ask for it — it is optional future work and not required to "get the DB back up and running" or to do your next data pull.

Keep the `.gz` file exactly as-is for now.

---

**Bottom line**: follow the plan below. Your historical scraped data is safely in `data/`. The DB backup is a bonus archive, not the primary source for the active tables.
